## What changed

### `/admin/warga`

- `src/app/api/admin/warga/route.ts`: one nested `tenant_users` query now
  embeds `users`, primary `user_houses`/`houses`, and
  `tenant_user_roles`/`roles`. The old primary-house and role batches are
  removed. `meta.joinedThisMonth` is now an accurate roster-wide count.
- `src/app/admin/warga/page.tsx`: search, blok filter and pagination are sent
  to the API (`q`, `blok`, `page`, `limit=30`) instead of fetching 100 rows
  and filtering in the browser. Search is debounced by 300 ms; page resets
  with the filter in one state update. Added page controls and an accurate
  “Menampilkan X–Y dari N” footer. The initial data request starts in
  parallel with the `/api/profile` access guard.

This fixes the old correctness bug where warga 101+ were invisible and
“Baru Bulan Ini” only counted the first 100 rows.

### Admin pages

`/admin`, `/admin/warga`, `/admin/users`, and `/admin/join-request` no longer
wait for `/api/profile` before starting their data request. Each data API
already enforces admin access on its own; the profile guard still controls
rendering and redirects, so authorization behavior is unchanged. This removes
one full profile round-trip from the critical path.

`/admin/users` also now:

- debounces its search input instead of issuing a request per keystroke,
- resets the page in the same update as the filter (no double request),
- uses the same debounced search state for both visible search inputs.

### Landing data (`src/app/landing/data.ts`)

- Profile: user + primary house in one query instead of two.
- Jualan: explicit column list instead of `select("*")`.
- Jasa: one nested service query replaces four follow-up queries for owners,
  categories and media. Removed three `console.log` debug lines.
- No cache semantics changed; published data is still read per request.

### `/kas-rt/house-status`

- Submitting or revoking an override patches the affected house in local
  state from the mutation response (`credited_months`,
  `credited_month_numbers`, reason, notes) using `isSettledByMonths`.
  The page no longer re-runs auth + 128 houses + 721 transactions + overrides
  after every adjustment. Manual refresh still refetches.
- Grouping/totals are memoized on `statuses`.
- Money semantics are untouched: overrides still credit months only, and
  `total2026` is never modified.

### Bundle splitting

- `/kas-rt/summary`: direct imports for light components; `chart.js`
  (`KasRtMonthlyChartV2`) and `html2canvas` (`KasRtExportButton`) are
  `next/dynamic` with `ssr: false` and layout-stable placeholders.
- `/kas-rt`: create/edit sheet, filter sheet and download sheet are loaded on
  first open. The `@/components/kas-rt` barrel was replaced with direct
  imports because it was pulling the form/NextUI code into the route.
- `/kas-rt/house-status`: direct import of the status card (the barrel was
  the source of ~107 kB of unused code).
- `/landing`, `/jualan`, `/jasa`: detail/create/edit modals are dynamically
  imported so they are not parsed before the grid paints.

## Round 2 — "instant load" pass (same day, after the first deploy)

Follow-up request: pages still felt slow (kas-rt, dashboard, other pages).
This round attacks the *server round trips* instead of the bundle, because
after the bundle split the remaining latency was dominated by sequential
Supabase REST calls that every request paid before anything could render.

### Server round trips removed

| Path | Before | After | Change |
| --- | --- | --- | --- |
| Session validation (every request) | 2 sequential calls | 1 nested call | **−50%** |
| `requireAdmin` (every admin API) | 2 sequential calls | 1 nested call | **−50%** |
| Kas RT permissions (page load) | 2 sequential calls | 1 nested call | **−49%** |
| Kas RT list + count | 2 sequential calls | 2 parallel calls | **−23%** |
| `GET /api/profile` | 10+ sequential calls | 2 parallel rounds | **−45% end to end** |
| Admin page guard | full `/api/profile` payload | `GET /api/admin/me` (1 call, 347 B) | **1 round trip, ~85% smaller** |
| `GET /api/notifications` | whole history (854 rows, ~190 kB) | 50 rows, ~22 kB, paginated | **~88% smaller** |

Measured locally (median of 5, service-role REST calls, same network as the
baseline): session 406 ms → 202 ms, kas permissions 323 ms → 164 ms, kas list
414 ms → 320 ms, `GET /api/profile` 2 149 ms → 1 229 ms (identical 1 959 B
payload, byte-for-byte equal JSON for all 66 users with a residence).

### What changed

- `src/lib/auth/session.ts`: the session row is read with the user's
  `status` embedded, so the approval-lock check no longer needs a second
  query. Every page and API call paid that query before.
- `src/lib/auth/admin-guard.ts`: `requireAdmin` is now a single nested
  query (`tenant_users` + `tenant_user_roles`).
- `src/app/kas-rt/data.ts`: permissions are one nested query; the transaction
  list and its exact count run in parallel.
- `src/app/api/profile/route.ts`: the user row, house links, owned-house
  links and badges are fetched in one batch; house members, residence roles
  and join requests in a second parallel batch. Output is unchanged
  (verified byte-for-byte for every user with a residence).
- `src/app/api/admin/me/route.ts` (new): one-query admin identity probe used
  by all 12 admin page guards instead of the full profile.
- `src/lib/api-client.ts`: short-lived response cache (30 s `/api/admin/me`,
  20 s `/api/profile`, 15 s `/api/admin/stats`) with in-flight de-duplication.
  Any write clears it, `cache: "no-store"` bypasses it, and a 401 clears
  everything. Repeat navigation between admin pages no longer re-asks the
  server.
- `src/app/api/notifications/route.ts` + `src/app/notifikasi/page.tsx`: the
  notification list is paginated (50 per page, “Muat lebih banyak”) and the
  unread badge comes from a total-count query, so the page no longer
  downloads and renders the entire history.

### Semantics

- Role checks are unchanged: the new admin guard derives roles from the same
  ACTIVE tenant memberships and ignores revoked assignments. Verified for all
  68 active tenant users: 0 differences in admin access, 0 differences in
  Kas RT submit permission.
- The admin dashboard balance is still computed from the same rows with the
  same filters; no aggregation, RPC or money rule was changed.

## Limitations

- No authenticated browser session was available, so authenticated route
  latency, LCP and INP were not measured in a real browser. Query timings use
  the same production queries with the service-role key; route JS is measured
  from `next build`.
- Timings are single-location network samples, not a benchmark suite.
- `/api/profile` is now two parallel rounds instead of a 10+ call waterfall,
  but it is still the heaviest shared endpoint. Admin pages no longer need it
  (`/api/admin/me` replaced it as the guard).
- The Vercel functions run in `iad1`; if the Supabase project lives in
  another region, every round trip pays the distance. Moving the functions to
  the Supabase region is the next big lever and needs the project region
  confirmed.

## Prioritized backlog

1. **Move the Vercel functions to the Supabase region.** The functions run in
   `iad1`; every database call pays the distance to the project. A
   `vercel.json` with the right region is a one-line change and can be bigger
   than all the query collapsing above. Needs the Supabase project region
   confirmed first.
2. **Admin stats aggregation.** 650 income + 114 expense rows are reduced in
   JS because PostgREST aggregates are disabled (`PGRST123`). Move to a view
   or RPC only with migration approval. The dashboard value itself is already
   cached client-side for 15 s.
3. **Article `content` payload.** Landing selects full markdown for 5 cards and
   strips it client-side. A server-computed preview would cut the landing
   payload, but needs a product decision on card text.
4. **Remove the duplicate search bar on `/admin/users`.** Both bars now share
   debounced state, but one is redundant; deleting it is a UI cleanup.
5. **Remove the unused recharts chart** (`KasRtMonthlyChart`) or at least its
   barrel export, so it cannot re-enter a bundle.
6. **Server-side role guard for admin routes.** Would remove the client guard
   round trip entirely, but changes role-check placement and needs approval
   against the existing auth semantics.
7. **Resident pages that still fetch after hydration** (`/organisasi`,
   `/jasa`, `/jualan`, `/profil`). Moving their first read to a server
   component would remove one client round trip each, like `/kas-rt` and
   `/landing` already do.
