## Confirmed findings

1. **Admin pages have an auth → data waterfall.**
   `/admin`, `/admin/warga`, `/admin/users`, and `/admin/join-request` each
   call `/api/profile` and only start their data request after it resolves.
   `/api/profile` itself runs 5+ queries for a user with one residence
   (user, house links, per-residence house/members/tenant/community,
   tenant_user/roles, owned-house join requests, badges). The data endpoints
   already enforce admin independently, so the two requests can be started in
   parallel without changing authorization.

2. **Admin warga search/pagination is incorrect beyond 100 rows.**
   The page requests `limit=100` once and filters client-side. With 68 active
   users this is currently masked, but it is a correctness bug: user 101+ is
   invisible, and “Baru Bulan Ini” is computed from the fetched page only.
   The API already supports `q`, `blok`, `sort`, `page`, `limit`, but the page
   never uses them. The API loads all active users plus two batched follow-up
   queries (houses, roles).

3. **Admin stats sums transaction rows in JS.**
   650 income + 114 expense rows (≈18 kB) are returned and reduced. The route
   already runs its eight stat queries in parallel. The cost is small at
   current volume; this is a payload/cleanup candidate, not the main bottleneck.

4. **Landing server data has internal waterfalls and over-fetching.**
   - Profile: user query → house query (2 sequential).
   - Jualan: tenant lookup → goods query; goods uses `select("*")`.
   - Jasa: tenant → services → owners → categories → media (4 sequential
     after tenant), plus three `console.log` debug lines.
   - Articles: 1 query, but selects full `content` for 5 cards (≈25 kB);
     the card UI currently uses `content` (stripped) as its text, so this
     cannot be dropped without a UI decision.

5. **House-status adjustment refetches the entire dataset.**
   After POST/DELETE the client calls `/api/kas-rt/house-statuses`, which
   re-runs auth/session checks, loads 128 houses, 721 transactions, and 5
   overrides server-side. The mutation already returns the new override
   fields, and overrides never touch money, so the updated house can be
   patched locally. Grouping (128 houses × 12 cells) is recomputed on every
   render and is not memoized.

6. **Summary ships chart/export code in the initial bundle.**
   `KasRtSummaryV2Client` statically imports `chart.js` + `react-chartjs-2`
   and `html2canvas` (via the export button). It also imports from the
   summary barrel, which re-exports the unused recharts chart. The initial
   chunk group contains a 193.5 kB chunk that includes these libraries.

7. **No caching was added.** All priority data is session-scoped except
   published articles. No cache semantics were changed in this pass.

## Limitations

- No authenticated test session was available locally, so baseline endpoint
  latency was measured by replaying the exact read queries with the
  service-role key rather than by calling the session-guarded route handlers.
  Route JS and data volumes are measured directly.
- Timings are single samples over the public internet and should be read as
  directionally comparable, not as a benchmark suite.
- No data was written and no migration/index was applied.
